# 侧边栏虚拟列表顶部缺行调查

本文记录 2026-09-17 对侧边栏虚拟列表偶发顶部缺行的调查、结构调整和再次复现时的取证方法。根因尚未通过运行时现场确认；结构调整减少了最可疑的生命周期分支，但不能在没有复现的情况下宣称问题已经修复。

## 2026-09-30 的处理决定

保活调整后仍出现顶部缺行，且内容不足一屏时无法通过滚动恢复。文件树和 Changes 因此改为普通文档流渲染全部展示行，移除虚拟范围计算、总高度占位和逐行绝对定位；折叠目录仍不生成子行。键盘导航与活动文件定位按真实行几何调整所属列表的滚动位置，不滚动侧栏祖先。

该方案消除了这两处因虚拟范围与原生滚动不同步而缺行的路径，不代表已经确认或修复 WebView 的独立绘制故障。Git 历史仍保留虚拟化：分页追加和搜索连续加载会累积提交，展开提交还会增加文件行。

另将文件树的目录域初始化与可见性监听、刷新拆开。`7891645e` 曾将 `active` 加入恢复目录缓存的 effect，导致普通切换仍会重建树数据和清理编辑状态；现在隐藏只停止展示监听并使过期读取失效，恢复在现有数据上刷新。真实目录或连接域变化仍重新初始化。

下文保留此前调查过程。再次发生文件树或 Changes 缺行时，应直接检查行 DOM、几何与绘制，不再采集这两处已移除的虚拟器状态；虚拟器相关取证只适用于仍采用虚拟化的列表。

## 大量改动时的性能边界

Changes 继续保留普通文档流和全部轻量文件行，右键菜单与文件提示由列表共享，行内操作只在悬停或选中时挂载。延迟挂载不替换文件按钮与滚动节点，避免按下鼠标或切换侧栏时丢失交互目标。

仓库状态清单与增删行数统计分别读取；隐藏面板不启动展示统计，旧批次退出后只追赶最新版本。被动恢复校验复用进行中的请求，真实文件失效仍补充读取；连续无变化和慢读取适当降低轮询频率。列表字段未变化时保留对象身份，但每次真实状态校验仍推进正文刷新版本，因为文件持续为 `M`、甚至增删行数不变时，正文仍可能改变。

运行真实桌面应用取证时遵循 [Tauri 运行时调试](ui-runtime-debugging.md)，检查范围与命令遵循 [检查与验证](testing.md)。

## 已确认现象

- 文件树没有被整体推到下方，而是顶部若干行没有显示；后续行仍处于各自应有的纵向位置。
- 目标文件树没有被用户滚动过，故障出现时滚动条位于顶部。
- 一旦产生滚动，原空白区域立即恢复显示。
- 故障通常发生在浏览 Git 历史和 diff、再切回文件管理器之后，但没有稳定的最小操作序列。
- Changes 在改动文件很多时曾出现相似的顶部缺行，是否与文件树同源仍未确认。
- 2026-09-16 的 `7f020cff` 将虚拟行从 `top: 0 + translateY(start)` 改为 `top: start`，之后文件树仍发生过故障。行定位表达方式不是本次已确认的根因。

截图中第一条可见目录是 `dist`。按当时工作区排序，它之前约有十个目录；文件树行高为 24 CSS px，截图空白高度也接近这些行原本占据的高度。这更符合“顶部索引没有生成或没有绘制”，不符合列表内容整体位移。

## 调查结论边界

当前最强假设是浏览器真实滚动位置与虚拟器内部偏移短暂不同步：真实 `scrollTop` 已在 0，虚拟器仍按非零 `scrollOffset` 选择范围。以行高 24、overscan 8 计算，若内部偏移约为 432 px，可见起始索引约为 18，加入 overscan 后首个生成索引约为 10，与截图形态吻合。第一次滚动会让虚拟器重新读取真实偏移并生成顶部行。

这条推断尚缺故障现场数值，不能写成已证实根因。另一个仍成立的分支是：顶部行 DOM、范围和几何都正确，但 WebView2 在侧栏恢复后没有绘制这些像素，滚动触发了重绘。

现有静态证据已经降低以下方向的优先级：

- 普通行高误差或 overscan 太小不能解释真实滚动在顶部时稳定缺少最前面的行。
- 当前生产 bundle 直接调用 `getVirtualItems()`，没有把结果按稳定 virtualizer 实例缓存，因此 React Compiler 不是首要候选。
- Changes 分区动画可能造成其独立故障，但文件树不经过这套动画，不能单独解释两处现象。
- Explorer 的活动文件定位只接收普通编辑器和 Markdown 页面路径；单纯浏览 Git diff 或历史文件页面不会通过此入口触发文件树自动滚动。

## 调整前的高风险生命周期

侧边栏池原先把已激活但不可见的容器移动到 `display: none` 的 depot，恢复时再把同一个容器移动回实际 sidebar host。React 实例保持不变，但滚动 DOM 经历了重新挂接、无布局祖先和再次布局。

文件树的 TanStack Virtual 实例也保持不变。锁定版本主要通过滚动事件更新内部 offset；滚动节点身份不变时，普通 React 更新不会因为父宿主变化而重新绑定该节点。若浏览器在隐藏、内容收缩或重挂接过程中夹紧了原生滚动位置而没有产生对应事件，内部范围可保持旧值直到下一次真实滚动。

Changes 还有另一条生命周期：Source Control 关闭时组件在所有 Hook 之后返回 `null`，导致其滚动节点被销毁，而 virtualizer 实例继续存在。重新打开后会创建新的滚动节点。

## 2026-09-17 的结构调整

本次调整建立以下不变量：

1. 侧边栏视图首次激活后，容器长期留在所属的 primary 或 secondary 真实 host。
2. 普通视图切换只更新 `visibility`、`pointer-events`、`inert` 和 `aria-hidden`，不移动 DOM。
3. 只有用户明确把容器移到另一侧栏时，才将容器重挂到另一个真实 host。
4. Source Control 的数据状态与可见性分离；仓库、变更数据和分区状态不变时，普通侧栏切换不再销毁 Changes 滚动节点和提交输入节点。`open` 继续控制面板手动刷新以及 Graph 活动、展示；共享仓库控制器仍运行，为文件装饰等功能提供数据。
5. 虚拟行继续使用 `top: start`。没有增加 `measure()`、滚动补偿、伪造滚动事件、额外 rAF 或扩大 overscan。

相关实现位于：

- `src/modules/sidebar/SidebarViewPool.tsx`
- `src/modules/source-control/SourceControlPanel.tsx`
- `src/modules/source-control/useSourceControlPanel.ts`
- `src/modules/sidebar/SidebarViewPool.test.tsx`
- `src/modules/source-control/SourceControlPanel.test.tsx`

`5c364334` 删除了面板外层的 `return null`，但遗漏了 Hook 中的 `closed` 状态：隐藏时仍退出 `ready` 分支并销毁 Changes 滚动节点。后续修正移除可见性对数据状态的影响，补齐上述第 4 项。

保活约束针对普通侧栏切换，不要求冻结真实业务变化。Explorer 内部搜索、项目根或连接状态变化，以及 Changes 分区折叠、clean/dirty 切换仍可能改变展示树；Graph 保留现有启停和滚动恢复逻辑，不在本次调整中统一改造。

回归测试覆盖容器 DOM 身份和父宿主，以及真实 Changes 面板在隐藏期间和恢复后的滚动节点、提交输入节点身份与输入选区。Changes 测试在修正前因隐藏时滚动节点被卸载而失败；这类组件测试验证生命周期，不证明真实 WebView 的缺行已经修复。

首次结构调整时没有启动应用或调试进程。当时验证结果为：侧边栏与 Source Control 的 14 个测试文件共 62 项测试通过，TypeScript 检查通过，改动文件的 Biome lint 和格式检查通过；全库 lint 仅报告已有警告。

补齐 Changes 保活后，侧边栏与 Source Control 的 15 个测试文件共 63 项测试通过，TypeScript 检查及改动代码的 Biome lint、格式检查通过。本次仍未启动应用或调试进程，偶发缺行是否消失仍待实际使用验证。

## 上游与 VS Code 对照

上游从最近审查边界 `f675a713` 到 `d3c8fd70` 的 106 个提交，以及同期更新的相关 PR 中，没有侧边栏虚拟列表恢复或顶部缺行修复。上游仍使用 transform 放置虚拟行，并在切换侧栏时按活动视图重新挂载组件，因此没有下游稳定面板池的同一条生命周期。

上游将 `@tanstack/react-virtual` 更新到 3.14.11、virtual-core 更新到 3.17.9；对应变更处理 end-anchored 列表补偿、滚动 debounce 清理和过期测量，不匹配当前固定行高、start-anchored 文件树。

VS Code 同样会把非活动 Composite 移出 DOM，但它有明确的 `setVisible` 和 `layout` 恢复协议，并由自己的 ListView/ScrollableElement 持有滚动与渲染范围。Terax 不复制这套滚动模型；本次通过避免普通切换时移动 DOM 来保持实现简单。

## 再次复现时的现场取证

发现空白后，先不要滚动、刷新、调整窗口、切主题、调用 `measure()` 或重新切换侧栏。先保存截图，并记录构建 SHA、WebView2 版本、系统缩放、应用缩放、窗口尺寸和触发前操作。

随后一次性记录以下快照，避免高频逐帧日志：

| 分组 | 必须记录 |
| --- | --- |
| 原生滚动 | `scrollTop`、`scrollHeight`、`clientHeight` |
| 虚拟器 | `scrollOffset`、`scrollRect.height`、范围起止索引、首个 virtual item 索引、总高度 |
| DOM 范围 | 最小和最大 `data-virtual-row-index`、顶部若干行是否存在 |
| 节点身份 | 滚动节点编号、父 `data-sidebar-view-host`、`isConnected`、切换前后是否为同一节点 |
| 几何 | 滚动视口、尺寸容器、首行和首个可见行的 rect 与计算样式 |
| 遮挡与裁剪 | 祖先的 `display`、`visibility`、`overflow`、`translate/transform`，以及空白区域的 `elementFromPoint` |

文件树已有 `data-virtual-row-index`。若需要为 Changes 增加临时诊断标记，应同时标记列表名称、索引和 key，避免把 Graph 行误认为 Changes 行。诊断记录应有容量上限，结束后删除，不把 DOM 节点长期保存在日志中。

现场按以下规则分流：

| 现场 | 结论方向 |
| --- | --- |
| `scrollTop` 接近 0，内部 `scrollOffset` 非零，首个 DOM/virtual 索引大于 0 | 确认滚动状态与虚拟范围不同步 |
| 两种 offset 都接近 0，但首个 virtual 或 DOM 索引大于 0 | 检查范围缓存、数据索引与编译输出 |
| 索引 0 DOM 存在，但 rect、祖先位移或裁剪错误 | 检查宿主布局、分区动画和 CSS |
| 索引 0 DOM、几何、可见性和遮挡均正确，但像素缺失 | 转向 WebView2 绘制或合成调查 |

保存快照后再滚动，并对比滚动前后究竟变化了哪一类状态。若只有像素变化而 DOM、范围和几何都未变化，才有充分理由提高绘制问题优先级。

## 有针对性的复现范围

主路径始终从未手动滚动、真实位置在顶部开始：

1. 文件树保持顶部，切到 Source Control，再立即切回。
2. 文件树保持顶部，浏览提交和 diff，再切回。
3. 大量 Changes 保持顶部，切走再切回。
4. 单独测试 Changes 折叠、展开和 clean/dirty 数据切换，不能用这些结果替代文件树结论。
5. 单独测试容器在 primary 与 secondary 间移动；这仍会发生一次真实 DOM 重挂接，与普通切换不是同一路径。

没有稳定复现时，若干轮未出现故障不能证明已经修复。不要把深滚动后的另一个空白问题当成本故障，也不要以强制滚到顶部、永久扩大 overscan 或滚动 1 px 作为正式修复。文件树与 Changes 取消虚拟化是上文明确选择的结构简化，不作为根因已确认的证据。
